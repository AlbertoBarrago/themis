# 0011. `ordito tests`, `ordito approve tests` and the lock

Status: accepted (2026-10-06)

## Decision

### Test author

- New internal role `test-author` (`.ordito/agents/test-author.md`, generated by `init`). It
  uses the `models.planner` tier, so the spec format does not change.
- The agent gets read-only tools (to look at the scaffold) and returns structured output
  `{ files: [{ path, content }], questions: [{ text, severity }] }`. **Ordito writes the
  files**, never the agent: Ordito controls the paths and checks everything before writing.
- Checked mechanically (`src/acceptance/validate.ts`), with errors sent back to the agent up
  to 3 attempts (same loop as the planner, `src/agents/structured.ts`):
  - paths are relative, under `tests/acceptance/`, safe characters only, no `..`;
  - only TypeScript (and JSON fixtures), at least one `*.test.ts`, max 256 KiB per file;
  - every criterion has a `describe("AC-<n>: ...")`, no unknown criterion, no near-miss
    names (`AC-1 title`, `AC-01:`);
  - no forbidden marker (same list as the guard; a test keeps them in sync).

### No staging directory

This supersedes the staging directory decided at kickoff (point 5). Staging existed because
the agent-side deny rules would block an agent writing `tests/acceptance/`; since Ordito
writes the files, tests go straight to `tests/acceptance/`, where the human reviews them and
may edit them before approval. The contract is the human's until it is locked.

### Preconditions and replacement

- `ordito tests` requires an approved plan whose spec digest matches the current spec.
- It refuses when `tests/acceptance/` is not empty or the contract is locked. `--force`
  replaces the directory and removes the lock, only after a valid answer came back, so a
  failed regeneration leaves the previous contract intact.
- State lives in `.ordito/tests.json` (`status`, spec digest, files, questions).

### Approval and lock

`ordito approve tests`:

1. requires an approved plan and an unchanged spec;
2. re-validates the files on disk (the human may have edited them);
3. refuses blocking questions unless `--force`;
4. writes `.ordito/lock.json` (format in ADR 0007) with the digests of every file under
   `tests/acceptance/`, the spec, `.ordito/verify.sh`, `.ordito/guard.mjs`, the tool
   configuration (`tsconfig.json`, `biome.json`, `vitest.config.ts`) and the agent adapter's
   configuration (`.claude/settings.json`) when present. `base` is `git rev-parse HEAD`, or
   `null` without a commit (the guard then scans every source file for markers).

## Consequences

- First real run (webhook example, `opus`): 7 files, about 1100 lines, valid on the first
  attempt, one genuine blocking question (database credentials missing from the decisions),
  but 896 s and $3.08 for a single structured answer. The test author therefore gets a
  45-minute timeout. If this becomes a bottleneck, generate one criterion per call (in
  parallel) around a shared harness.

- Acceptance tests cannot be type-checked or run at the gate: the implementation does not
  exist yet. Their correctness is the human's review; the verifier will exercise them from M4.
- `ordito init` must be re-run on projects initialised before M3 to get `test-author.md`.
