# Webhook ingestion service

Receives webhooks from an upstream provider, validates and deduplicates them, stores them
durably and forwards them to an internal consumer with retries and a dead-letter state.

## Decisions

- Runtime: Node.js 22 or later, TypeScript in strict mode, ESM. HTTP framework: Fastify 5.
  Database driver: `pg`. No ORM.
- Storage: PostgreSQL 16, defined in `docker-compose.yml` as service `postgres`. The host
  port comes from `POSTGRES_PORT` (default `5432`) and the compose project name from
  `COMPOSE_PROJECT_NAME`, so several copies can run side by side.
- Migrations: plain SQL files in `migrations/`, applied in lexical order by
  `npm run migrate`. Applying them twice is a no-op. The connection string comes from
  `DATABASE_URL`.
- Public interface: `src/app.ts` exports
  `createApp(config: AppConfig): Promise<App>`, where
  `App = { server: import("node:http").Server; close(): Promise<void> }`. The returned
  server is not listening yet: the caller calls `listen`. `close()` stops the server and
  any delivery in progress, and releases database connections.
- `AppConfig` is exported from `src/app.ts` with exactly these fields:
  `databaseUrl: string`, `webhookSecret: string`, `forwardUrl: string`,
  `forwardTimeoutMs: number`, `retry: { maxAttempts: number; baseDelayMs: number }`.
- Ingestion endpoint: `POST /webhooks`. The request body is JSON. Successful responses are
  `202` with body `{ "id": "<event id>" }`. Event ids are UUIDs generated by the service.
- Signature: header `X-Signature: sha256=<hex>` where `<hex>` is the HMAC-SHA256 of the raw
  request body bytes keyed with `webhookSecret`. Comparison is constant time.
- Payload: a JSON object with a non-empty string `type` and an object `data`. Other fields
  are allowed and stored as received. Maximum body size: 1 MiB.
- Errors are JSON `{ "error": "<code>" }` with these codes: `invalid_signature` (401),
  `invalid_payload` (400), `missing_idempotency_key` (400), `payload_too_large` (413),
  `idempotency_conflict` (409), `not_found` (404).
- Event resource: `GET /events/:id` returns `200` with
  `{ "id", "type", "status", "attempts", "receivedAt", "payload" }`. `status` is one of
  `pending`, `delivered`, `dead_lettered`. `receivedAt` is an ISO 8601 timestamp.
  `attempts` counts forwarding attempts made so far.
- Delivery runs inside the service process, asynchronously from the ingestion request.
  Events still `pending` when the service starts are resumed.
- Forwarding: `POST` to `forwardUrl` with the original body bytes and the headers
  `Content-Type: application/json`, `Idempotency-Key` (as received) and `X-Event-Id`.
  Any `2xx` response is a success. Any other status, a network error or no response within
  `forwardTimeoutMs` is a failed attempt.
- Retry: after failed attempt `n` the next attempt waits `baseDelayMs * 2^(n-1)`.
  `maxAttempts` counts every attempt, including the first.
- Out of scope: authentication on `GET /events/:id`, multi-tenancy, metrics, ordering
  guarantees between events.

## Test harness

Acceptance tests start the service through `createApp` on an ephemeral port, against the
compose PostgreSQL with a clean schema per test file, and point `forwardUrl` at a stub HTTP
server they control. They use small `baseDelayMs` and `forwardTimeoutMs` values so retries
complete within a few seconds.

## AC-1 Signature and payload validation
Depends: none
- Given a request to `POST /webhooks` whose `X-Signature` is missing or does not match the body
- When the service receives it
- Then it responds `401` with error `invalid_signature`
- And nothing is stored
- Given a correctly signed request whose body is not valid JSON, is not an object, lacks a non-empty string `type` or lacks an object `data`
- When the service receives it
- Then it responds `400` with error `invalid_payload`
- Given a correctly signed body larger than 1 MiB
- When the service receives it
- Then it responds `413` with error `payload_too_large`

## AC-2 Durable persistence
Depends: AC-1
- Given a correctly signed, valid request with an `Idempotency-Key` header
- When the service receives it
- Then it responds `202` with a UUID `id`
- And `GET /events/<id>` returns the event with its `type`, the received `payload`, a `receivedAt` timestamp and `attempts` equal to the attempts made so far
- Given an accepted event
- When the service is closed and a new instance is created on the same database
- Then `GET /events/<id>` on the new instance still returns the event
- Given an id that does not exist
- When `GET /events/<id>` is called
- Then it responds `404` with error `not_found`

## AC-3 Deduplication by Idempotency-Key
Depends: AC-2
- Given a correctly signed, valid request without an `Idempotency-Key` header
- When the service receives it
- Then it responds `400` with error `missing_idempotency_key`
- Given an event accepted with key `K`
- When a request with key `K` and a byte-identical body arrives
- Then it responds `202` with the same `id` as the first request
- And no second event is stored and no second delivery happens
- Given an event accepted with key `K`
- When a request with key `K` and a different body arrives
- Then it responds `409` with error `idempotency_conflict`
- Given two concurrent identical requests with the same new key
- When both are processed
- Then both responses carry the same `id` and exactly one event is stored

## AC-4 Forwarding
Depends: AC-2
- Given an accepted event and a consumer that responds `200`
- When delivery runs
- Then the consumer receives exactly one `POST` with the original body bytes, `Content-Type: application/json`, the original `Idempotency-Key` and `X-Event-Id` equal to the event id
- And the event reaches status `delivered` with `attempts` equal to 1
- Given an event still `pending` when the service is closed
- When a new instance is created on the same database
- Then the new instance delivers it

## AC-5 Retry with exponential backoff
Depends: AC-4
- Given `maxAttempts` 4 and a consumer that responds `503` twice and then `200`
- When delivery runs
- Then the consumer receives exactly 3 requests
- And the delay before the second and third requests is at least `baseDelayMs` and `2 * baseDelayMs` respectively
- And the event reaches status `delivered` with `attempts` equal to 3
- Given a consumer that does not respond within `forwardTimeoutMs`
- When delivery runs
- Then the attempt counts as failed and is retried

## AC-6 Dead-letter after exhausted retries
Depends: AC-5
- Given `maxAttempts` 3 and a consumer that always responds `500`
- When delivery runs
- Then the consumer receives exactly 3 requests
- And the event reaches status `dead_lettered` with `attempts` equal to 3
- And no further delivery is attempted for it, including after the service restarts
